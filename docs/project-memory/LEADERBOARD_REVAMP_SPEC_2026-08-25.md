## 2026-08-26 session, continued — preview bug fixed (timeline anchor)

Shailesh reported both prototype artifacts only showed the settled end-state, never the actual choreography. Root cause: `startTime` was captured synchronously the instant `start()` ran, not anchored to the first frame that actually painted. A sandboxed preview iframe can take a beat to become visible, and a hidden/off-screen iframe has its `requestAnimationFrame` callbacks throttled or paused entirely by the browser the whole time real wall-clock time keeps moving -- so by the time the first frame actually rendered, elapsed time could already be past the whole ~15s/~9s arc, landing straight in the idle "everything is done" state and staying there (idle drift looks like a static end screen). Fixed in both files by anchoring `startTime` inside the first real `frame(now)` callback instead of at `start()` time -- republished to the same two artifact URLs, no new links.

## 2026-08-26 session, continued — actual root cause of "only shows the end state"

The timeline-anchor fix above didn't resolve it because it wasn't the real cause. The real cause: both scenes had a `prefers-reduced-motion: reduce` branch that hard-jumped straight to the idle end frame and never scheduled another animation frame at all (`if(!reduced && !ended) rafId=requestAnimationFrame(frame)` -- when `reduced` is true, this simply never re-fires after frame one). Whatever is evaluating `window.matchMedia('(prefers-reduced-motion: reduce)')` in Shailesh's review environment is returning true, so every load hit that branch. Fixed by removing the hard skip entirely -- the full sequence now always plays regardless of that media query, since this is a one-time few-second reveal being actively reviewed, not persistent ambient motion the setting is meant to guard against. Vestibular-relevant effects (screen shake, flash/chromatic-aberration pulses) are still dialed down (not zeroed) under that setting via a `reducedAmp` multiplier, so the accessibility intent isn't simply discarded -- it's just no longer allowed to hide the cutscene entirely. Republished to the same two artifact URLs again.

1. **On-screen text ("two circles joining etc" / "n=1,2,3 till infinity"): intentional, not a glitch.** Both are deliberate on-screen call-outs of each scene's core visual metaphor:

Raised the cap to 2.5x DPR / 6 megapixels in both scenes (a short, occasional full-screen cutscene can afford the extra GPU budget) and republished to the same two artifact URLs.

## 2026-08-31 session -- superadmin DB Search tool built (resolves the real-data verification gap from the 2026-08-28 entry)

Follow-up to the 2026-08-28 entry's flagged gap: real DPS leaderboard data was never confirmed end-to-end because the only DB reachable from a Cowork session is a stale, empty local sqlite file, and production is a separate Postgres instance those sessions can't reach directly. **Built exactly that**, per their spec:
- Backend: `POST /api/admin/db-search` in `routes_admin.py`, gated by the same `admin_dep = require_roles("SUPER_ADMIN", "ADMIN")` every other admin route uses. Two independent enforcement layers, not just one: (1) app-level regex validation -- single statement only (rejects any semicolon), must start with `SELECT`/`WITH`, blocklist of write/DDL/session keywords as whole words (`INSERT`, `UPDATE`, `DELETE`, `DROP`, ..., `INTO` to catch `SELECT ... INTO`, `SET`); (2) DB-level -- runs on its own dedicated engine with `NullPool` (never the shared app connection pool, so a read-only transaction flag can never bleed into an unrelated later request reusing a pooled connection) and, on Postgres, opens with `SET TRANSACTION READ ONLY` + a 5s `statement_timeout`, so Postgres itself refuses any write even if the regex has a gap. Every user query is wrapped in `SELECT * FROM (...) LIMIT 200` server-side regardless of what the user typed, and every run (success or failure) is written to `AuditLog` with the admin's user id and the exact query text, since this can surface arbitrary student PII.
- Frontend: `frontend/app/admin/db-search/page.tsx`, gated by `useProtectedPage(["ADMIN", "SUPER_ADMIN"])`, wrapped in `<AppShell>` per the established convention for every other admin page (confirmed by checking all 17 existing admin pages -- 100% wrap with AppShell; this is a deliberate contrast with the DPS/Mock leaderboard student pages, which intentionally do NOT use AppShell since they are full-bleed immersive pages, not nav-shell pages). Textarea + Run button (Ctrl/Cmd+Enter), results as an HTML table, row cap and truncation noted in the UI, an explicit PII warning banner.
- `frontend/lib/api/admin.ts`: added `runAdminDbSearch()` client function.
